## 2. 의사결정 기록 (Architecture Decision Records)

### ADR-1. 화면: Streamlit vs React + FastAPI
| 선택지 | 장점 | 단점 |
|---|---|---|
| **Streamlit (채택)** | Python만으로 완성, 채팅·업로드 위젯 기본 제공, GitHub 연동 무료 배포 | 디자인 자유도 낮음, 화면이 바뀔 때마다 스크립트 재실행 |
| React + FastAPI | 디자인·성능 자유도 | 두 개 앱 개발·배포, 4주 안에 테스트·개선까지 하기 어려움 |

**결정**: 이 프로젝트의 핵심 평가는 화면 완성도가 아니라 **AI 활용과 사용자 피드백 반영**이다. 개발 시간을 AI 기능과 테스트에 쓰기 위해 Streamlit을 택했다. 재실행 비용은 `st.cache_resource`(DB·클라이언트)와 RAG 인덱스 캐시로 줄였다.

### ADR-2. Agent: 직접 구현 vs LangChain/LangGraph
| 선택지 | 장점 | 단점 |
|---|---|---|
| **Function Calling 직접 구현 (채택)** | 약 100줄, 동작을 한 줄씩 설명 가능, 의존성·버전 충돌 없음, 테스트 쉬움 | 복잡한 다중 Agent 흐름은 직접 만들어야 함 |
| LangChain / LangGraph | 다양한 컴포넌트 | 추상화 계층이 많아 오류 원인 파악이 어렵고, 버전 변화가 잦음 |

**결정**: 도구 3개짜리 단일 Agent에는 프레임워크가 과하다. "Agent가 어떻게 도구를 고르고 실행하는지"를 발표에서 코드로 직접 보여줄 수 있는 것이 더 큰 가치다.

### ADR-3. 벡터 검색: numpy 전수 계산 vs Vector DB(Pinecone, Chroma)
- 규모 계산: 사용자당 자료 최대 10개 × 400조각 = 4,000개 × 1,536차원 float32 ≈ **24MB**(최대치), 일반적으로 수백 개 수준 → 내적 계산은 수 ms
- Vector DB는 외부 서비스 가입·키 관리·동기화가 추가되고, Chroma는 무료 배포 서버의 임시 디스크에서 데이터가 사라진다.

**결정**: 임베딩을 기존 DB에 함께 저장하고 numpy로 계산한다. 사용자가 크게 늘면 같은 Supabase에서 `pgvector` 확장으로 옮길 수 있다(이전 경로 확보).

### ADR-4. DB: SQLite + PostgreSQL 이중 지원
- Streamlit Community Cloud의 디스크는 **재시작·재배포 시 초기화**되므로 SQLite 파일만 쓰면 장기 기억이 사라진다 → Long-term Memory가 성립하지 않음.
- 로컬 개발·테스트는 설치 없는 SQLite가 편하다.

**결정**: `DATABASE_URL` 하나로 전환되는 얇은 DB 계층(`db.py`)을 만들었다. 두 DB에서 같은 SQL이 돌도록 PK는 UUID 문자열, 시각은 ISO 문자열, 자리표시자는 자동 변환한다. 배포는 무료인 Supabase PostgreSQL을 쓴다.

### ADR-5. 사용자 식별: 닉네임 + PIN vs 소셜 로그인
| 선택지 | 장점 | 단점 |
|---|---|---|
| **닉네임 + PIN (채택)** | 이메일·실명 미수집(개인정보 최소화), 테스터 가입 10초 | PIN 분실 시 복구 불가 |
| Google 로그인 | 편리, 보안 | 이메일 수집, OAuth 설정 복잡 |

**결정**: 테스트 기간 서비스에서는 **개인정보를 받지 않는 것**이 가장 안전하다. PIN은 PBKDF2 해시로 저장하고, 로그인 실패 5회 시 세션을 차단한다. 정식 서비스로 확장할 때 소셜 로그인을 추가한다.

### ADR-6. 배포: Streamlit Community Cloud vs Render vs Hugging Face Spaces
| 선택지 | 장점 | 단점 |
|---|---|---|
| **Streamlit Community Cloud (채택)** | 무료, GitHub 저장소 선택만으로 배포, push 시 자동 재배포, Secrets 관리 화면 | 일정 시간 미접속 시 잠자기, 디스크 비영구(→ ADR-4로 해결) |
| Render | 범용 | 무료 플랜 잠자기·설정 더 많음 |
| Hugging Face Spaces | AI 데모에 익숙 | 영구 저장소 유료 |

### ADR-7. 자동화: n8n
- 학습 목표 "노코드 자동화 도구와 Python을 조합한 서비스 구축"을 충족하면서, 사용자 테스트 기간에 실제로 쓸모 있는 파이프라인(피드백 → 시트 → 팀 알림)을 만든다.
- Python 앱은 Webhook 호출만 하고, 시트 기록·알림 로직은 n8n에서 노코드로 바꿀 수 있다. Webhook이 실패해도 피드백은 DB에 먼저 저장되므로 서비스에 영향이 없다.

### ADR-8. 모델 선택: `gpt-5.4-mini`
- 요구: 도구 호출 정확도, JSON 출력, 한국어, **저렴한 비용**(학생 예산), 빠른 응답
- 추론형 모델이므로 `reasoning_effort=low`로 지연·비용을 줄였다. 비추론 모델로 바꾸면 `REASONING_EFFORT=off`, 지원하지 않는 모델에서는 자동으로 파라미터를 빼고 재시도한다.
- 모델은 설정값이므로 테스트 결과(속도·품질 피드백)에 따라 교체하고, 그 결과를 이 문서에 추가 기록한다.
